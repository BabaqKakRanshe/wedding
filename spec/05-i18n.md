# 05 — Internationalization

## Languages

Three locales, equal weight. **No fallback to English** — English is out of scope.

| Code | Language | Default for browser locale |
|---|---|---|
| `ru` | Russian | `ru*` |
| `ja` | Japanese | `ja*` and **anything not matching `ru*` or `ko*`** (couple lives in Japan; safest neutral default) |
| `ko` | Korean | `ko*` |

## Detection and persistence

1. On first visit, read `navigator.language`, lowercase, take prefix before `-`.
2. Map to `ru` / `ko` if it matches, otherwise `ja`.
3. Store the resolved code in `localStorage` under key `wedding-lang`.
4. Manual switcher click overwrites `wedding-lang` and re-renders text immediately.
5. On subsequent visits, `localStorage` wins over `navigator.language`.

## Switcher UI

Fixed top-right corner. Three pills: `RU · 日本語 · 한국어`. Always all three visible. Active pill is filled with `--accent-sea`, others are outlined. Click → set language, no animation, no reload.

The switcher is also repeated in the footer for users who scroll all the way down.

## String storage

- One JSON file per language under `src/i18n/`: `ru.json`, `ja.json`, `ko.json`.
- Flat keys with dot-paths: `cover.subline`, `schedule.16.label`, `rsvp.field.name.label`.
- DOM elements with translatable text carry `data-i18n="cover.subline"`. A small JS function walks the DOM on language change and replaces `textContent`.
- For attributes (`alt`, `aria-label`, `placeholder`), use `data-i18n-attr="placeholder:rsvp.field.name.placeholder"`.
- `<html lang="…">` is updated on every switch (drives font selection via CSS `:lang()`).

## Source of truth

`spec/02-content.md` is the canonical content source. The JSON files mirror it. When adding/changing copy:

1. Edit `02-content.md` first.
2. Update all three JSON files.
3. Update referencing template/markup if the key changed.

Translations into JA/KO from RU original are TBD — needs native speaker review before launch (likely the groom for KO, a friend for JA, or the couple themselves since they live in Japan).

## Locale-sensitive formatting

Date and deadline strings are stored as **literal pre-formatted strings** in the JSON files (see `02-content.md` table), not generated via `Intl.DateTimeFormat` — avoids cross-browser quirks and gives the bride direct control over the wording.

Numbers (countdown digits) are plain ASCII in all three locales — no localised digits.

## Default-language ambiguity

Default = `ja` for non-RU/KO browsers because the couple lives in Japan and most uncategorised guests are likely Japanese-speaking. **Open question:** confirm with bride that this is the right neutral default (see `99-open-questions.md`).
